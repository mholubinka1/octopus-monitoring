# Periodic consumption backfill re-fetches the full retention window, accepting the existing cursor race

Before this change, a full re-fetch of the retention window only happened via `startup()` (`app/main.py`), so a day that fell behind the hourly `consumption_refresh` cursor, or a permanent gap Octopus never backfills (see [ADR-0009](0009-day-completeness-guard-standing-charge-fallback.md)), had no periodic catch-up mechanism on a long-running, rarely-restarted container. `consumption_backfill` now runs `startup()`'s same `ConsumptionRetriever.retrieve()` call daily at `DAILY_JOB_TIME`, rather than adding a query to find and target only the specific incomplete days.

Targeted re-fetch was considered and rejected: `retrieve(period_from)` has no single-day mode — it pages from `period_from` to now — so a permanent gap deep in the retention window would still require fetching from that old date forward, which is nearly as expensive as the full window. Since the case that matters most (a permanent, never-backfilled gap) gets little to no savings from targeting, the added complexity (a new completeness-guard query replicating ADR-0009's DST-aware logic) wasn't worth it. Both approaches are equally cheap for the common case (recent settlement lag, self-heals within a day or two).

This job shares its `ConsumptionRetriever` instance — and its in-memory `_latest_retrieved_date` cursor — with the hourly `consumption_refresh` job, so their background worker threads can genuinely run concurrently. This is deliberately left unguarded: both threads compute `latest_retrieved_date` as the max `end` timestamp of whatever they fetched, and both upsert idempotently keyed on `energy + interval start`, so whichever thread finishes last still leaves a correct cursor value and correct rows. This mirrors the already-accepted race between the yearly-comparison backfill and the eager pricing sync at startup (see the comment in `main.py`'s `main()`).
